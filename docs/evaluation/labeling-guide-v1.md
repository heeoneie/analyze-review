## 0. 이 문서의 지위

**이 체계는 모델 출력을 한 건도 보기 전에 확정했다.**

모델이 자주 틀리는 것을 보고 카테고리를 쪼개거나 합치면, 그 뒤에 나오는 정확도는
"모델이 잘한 것"이 아니라 "기준을 모델에 맞춘 것"이 된다. 측정이 아니라 연출이다.

따라서:

- 라벨링 도중에도, 라벨링이 끝난 뒤에도 이 문서를 고쳐서 v1 수치를 바꾸지 않는다.
- 체계에 실제 결함이 발견되면 **v2 를 새로 만들고**, 결함 내용·수정 이유·수정 시점을
  [`docs/evaluation/taxonomy-changelog.md`](./taxonomy-changelog.md) 에 적고,
  **v1 수치와 v2 수치를 리포트에 둘 다 남긴다.** v1 을 삭제하지 않는다.
- `core/eval/taxonomy.py` 의 `TAXONOMY_VERSION` 을 올리지 않은 변경은 금지한다.

라벨은 **사람이 직접 단다.** LLM 으로 ground truth 를 만들지 않는다. LLM 이 만든
라벨로 LLM 분류기를 평가하면 "모델이 자기 자신과 얼마나 일치하는가"를 재게 되고,
그 숫자는 정확도가 아니다.

> 참고: 기존 `evaluation/evaluation_dataset.csv` 의 `manual_label` 은 사람이 단 것이
> 아니다. 사람용 `notes` 컬럼은 100건 전부 비어 있는 반면 LLM 출력 필드인
> `confidence`·`reasoning` 은 100건 전부 채워져 있다. 그 파일은 ground truth 로
> 쓰지 않는다.

## 1. 카테고리 (13종, 닫힌 집합)

이 13개 밖의 라벨은 만들지 않는다. 맞는 것이 없으면 `other` 이고,
그마저도 애매하면 규칙 **R10** 을 따른다.

### 불만 카테고리 (12종)

| 키 | 이름 | 단축키 | 포함 | 제외 |
|---|---|:---:|---|---|
| `taste` | 맛 | `1` | 음식 맛 자체에 대한 불만. 싱겁다/짜다/맵다/느끼하다/맛없다, 면이 불었다, 소스 배합이 이상하다, 예전 맛과 다르다 | 식어서 맛이 없으면 `temperature`. 이물질·상한 냄새는 `hygiene`. 양 때문에 아쉬우면 `portion` |
| `temperature` | 온도 | `2` | 도착 시점 온도 불만. 식었다/미지근하다/차갑다, 튀김이 눅눅해졌다, 국물이 안 뜨겁다 | 배달이 오래 걸렸다는 '시간' 자체는 `delivery_delay`. 둘 다면 **R4** |
| `portion` | 양 | `3` | 양이 적다, 건더기가 없다, 사진보다 적다, 1인분 같지 않다. '양 대비 비싸다'에서 양이 주어인 경우 | 품목이 통째로 빠진 것은 `missing_item`. 가격이 주어면 `price` |
| `hygiene` | 위생·이물질 | `4` | 머리카락·비닐·벌레 등 이물질, 상한 냄새/쉰내, 곰팡이, 덜 익음, 먹고 탈이 났다, 용기가 더럽다 | 단순히 맛없는 것은 `taste`. 용기 파손·국물 샘은 `packaging` |
| `missing_item` | 누락 | `5` | 주문한 메뉴가 안 왔다, 리뷰이벤트 서비스가 빠졌다, 단무지/소스/수저/포크 누락, 음료 누락 | 주문과 '다른' 것이 온 것은 `wrong_item`. 양이 적은 것은 `portion` |
| `wrong_item` | 오배송 | `6` | 주문과 다른 메뉴, 짜장 시켰는데 짬뽕, 맵기·옵션이 주문과 다름, 다른 집 음식 | 빠진 것은 `missing_item` |
| `packaging` | 포장 | `7` | 국물이 샜다, 용기가 깨졌다/찌그러졌다, 뚜껑이 열려 있었다, 음식이 쏟아져 흐트러졌다, 봉투가 터졌다 | 용기가 더러우면 `hygiene`. 포장 탓에 식었으면 **R5** |
| `delivery_delay` | 배달 지연 | `8` | 배달이 오래 걸렸다, 예상 시간보다 한참 늦었다, 조리 시작이 늦었다 | 식어서 온 것 자체는 `temperature`. 엉뚱한 곳에 둔 것은 `rider` |
| `rider` | 라이더 | `9` | 배달원 태도/말투, 문 앞 요청 무시, 엉뚱한 집 배달, 음식 분실, 초인종 안 누름, 던지듯 놓고 감 | 매장 직원·사장 응대는 `store_response`. 단순 지연은 `delivery_delay` |
| `store_response` | 매장 응대 | `0` | 전화 안 받음, 응대 태도 불친절, 환불/재배달 거부, 사장 답글이 성의 없음, 조리 요청사항 무시 | 배달원 응대는 `rider` |
| `price` | 가격 | `p` | 비싸다, 가성비 나쁘다, 배달비가 과하다, 값을 올렸다. '양 대비 비싸다'에서 가격이 주어인 경우 | 양이 주어면 `portion` |
| `other` | 기타 | `x` | 불만은 분명하나 위 어디에도 맞지 않음. 배달앱 자체 오류, 쿠폰/포인트 문제, 주차/출입 문제 | 애매하다는 이유로 쓰지 않는다 → **R10** |

### 비불만 (1종)

| 키 | 이름 | 단축키 | 포함 | 제외 |
|---|---|:---:|---|---|
| `no_issue` | 문제 없음 | `n` | 불만이 없는 리뷰. 칭찬, 중립적 감상, 재주문 의사. 별점이 낮아도 본문에 불만이 없으면 여기(**R2**) | '다음엔 ~해주세요' 형태의 개선 요청은 불만으로 본다(**R7**) |

### 제외 표시 (라벨 아님)

| 표시 | 단축키 | 용도 |
|---|:---:|---|
| `EXCLUDE` | `e` | 본문이 없거나(이모지·자음만·공백), 무슨 말인지 판정할 수 없는 리뷰. **분류 대상이 아니므로 분모에서 뺀다.** 제외 건수와 비율은 리포트에 반드시 적는다 |

## 2. 판정 규칙

애매한 케이스에서 **매번 같은 답이 나오게** 하는 것이 목적이다.
규칙이 서로 충돌하면 **번호가 작은 쪽이 이긴다.**

### R1 — 주라벨은 "가장 강하게 표현된 불만" 하나

여러 불만이 섞여 있으면, 손님이 **가장 강한 어조로** 말한 것을 주라벨로 한다.
강도가 비슷하면 **먼저 언급된 것**을 주라벨로 한다.

> "면은 좀 불었는데 **머리카락이 나와서 도저히 못 먹었어요**"
> → 주라벨 `hygiene` (강도가 압도적), 대체라벨 `taste`

기존 가이드(`docs/labeling_guide.md`)의 "글자 수가 많은 쪽" 규칙은 쓰지 않는다.
길게 쓴 것과 심각한 것은 다르다.

### R2 — 별점과 본문이 충돌하면 본문이 이긴다

별점은 라벨 근거가 아니다. 배달앱은 별점 인플레이션이 심해서 5점에도 불만이 섞이고,
1점인데 본문은 배달앱 불만인 경우도 있다. **본문에 쓰인 내용만 본다.**

> 별점 5 + "맛은 최고인데 **양이 너무 적어요**" → `portion`
> 별점 1 + "잘 먹었습니다" → `no_issue`

### R3 — 원인이 적혀 있으면 원인 쪽으로 간다

증상보다 손님이 지목한 **원인**을 라벨로 한다.

> "맛없어요" → `taste`
> "**식어서** 맛없어요" → `temperature`
> "**너무 늦게 와서** 다 식었어요" → **R4** 를 적용한다

### R4 — 지연과 온도가 같이 나오면 `temperature`

"늦게 와서 식었다"는 배달 외식업에서 가장 흔한 복합 불만이다.
손님이 실제로 손해 본 것은 음식 상태이므로 **주라벨 `temperature`,
대체라벨 `delivery_delay`** 로 고정한다.

단, 시간만 말하고 음식 상태를 말하지 않으면 `delivery_delay` 단독이다.

> "1시간 반 걸렸고 다 식어서 왔어요" → 주 `temperature` / 대체 `delivery_delay`
> "1시간 반이나 걸렸네요" → `delivery_delay`

### R5 — 물리적 원인이 있으면 물리적 원인 쪽으로 간다

> "국물이 새서 다 흘렀고 식었어요" → 주 `packaging` / 대체 `temperature`

### R6 — 양 vs 가격은 문장의 주어로 가른다

> "**양이** 이 가격에 너무 적어요" → 주 `portion` / 대체 `price`
> "이 **가격이면** 양이 더 나와야죠" → 주 `price` / 대체 `portion`

가를 수 없으면 `portion` 을 주라벨로 한다(임의 고정 — 일관성이 정확성보다 중요하다).

### R7 — 개선 요청은 불만으로 본다

"다음엔 ~해주세요", "~만 좀 더 ~하면 좋겠어요" 는 칭찬 뒤에 붙어도 불만이다.
해당 카테고리를 주라벨로 하고, 칭찬이 대부분이면 대체라벨 `no_issue` 를 붙인다.

> "맛있게 잘 먹었어요! 다음엔 **덜 짜게** 부탁드려요" → 주 `taste` / 대체 `no_issue`

### R8 — 요청사항 무시는 누가 무시했느냐로 가른다

> "덜 맵게 해달라고 했는데 그대로 왔어요" → `store_response` (주방이 무시)
> "문 앞에 놔달라고 했는데 벨 눌렀어요" → `rider` (라이더가 무시)

### R9 — 리뷰이벤트 서비스 품목은 `missing_item`

"리뷰 이벤트 만두 안 왔어요", "서비스 음료 빠졌어요" → `missing_item`.
배달앱 쿠폰·포인트 오류는 `other`.

### R10 — 20초 안에 못 정하면 `other` + 메모

한 건에 오래 붙들려 있으면 기준이 흔들린다. 20초 안에 주라벨이 안 나오면:

1. 주라벨 `other`
2. `notes` 에 왜 애매한지 한 줄 (예: "맛 불만인지 양 불만인지 불명")
3. 넘어간다

라벨링이 끝난 뒤 `other` + 메모가 있는 건들만 모아 한 번에 재검토한다.
**이때도 모델 출력은 보지 않는다.**

## 3. 대체라벨 (선택)

주라벨 외에 **"이걸로 분류해도 틀렸다고 하기 어렵다"** 싶은 라벨을 최대 1개 붙일 수 있다.
단축키는 `Shift` + 해당 카테고리 키다.

대체라벨은 채점을 두 가지로 낼 수 있게 해 준다:

| 채점 방식 | 정답 조건 | 성격 |
|---|---|---|
| **엄격(strict)** | 예측 == 주라벨 | 주 지표. 보수적 |
| **관대(lenient)** | 예측 ∈ {주라벨, 대체라벨} | 다중 이슈 리뷰에서의 과소평가 크기를 드러냄 |

두 수치를 **둘 다** 보고한다. 관대 수치만 쓰면 지표를 부풀리는 것이다.
대체라벨을 "혹시 몰라서" 남발하면 관대 수치가 무의미해지므로,
**리뷰 100건당 30건을 넘기지 않는 것**을 목표로 한다.

## 4. 라벨링 절차

```bash
# 1) 표본 추출 (층화)
python scripts/eval/build_sample.py --csv <리뷰CSV> --out evaluation/sample_v1.csv

# 2) 라벨링 (브라우저 UI, 단축키)
python scripts/eval/label_tool.py evaluation/sample_v1.csv

# 3) 재검사 신뢰도용 재라벨링 (3일 이상 지난 뒤)
python scripts/eval/label_tool.py evaluation/sample_v1.csv --mode retest
```

### 한 건 처리 순서 (목표 5~10초)

1. 본문을 읽는다. **별점은 보지 않아도 된다** (R2).
2. 불만이 없으면 `n`.
3. 불만이 있으면 가장 강한 것 하나를 고른다 (R1).
4. 애매하면 R3~R9 를 순서대로 본다.
5. 20초 넘으면 `x` + 메모 (R10).
6. 대체라벨이 떠오르면 `Shift`+키.

### 세션 관리

- **한 번에 60건을 넘기지 않는다.** 집중력이 떨어지면 기준이 흔들린다.
- 세션 시작 때마다 위 카테고리 표를 다시 훑는다 (도구 화면 우측에 항상 떠 있다).
- 도구는 키를 누를 때마다 CSV 에 즉시 저장한다. 중간에 닫아도 된다.

## 5. 재검사 신뢰도 (intra-rater reliability)

라벨러가 한 명이므로 rater 간 일치도(inter-rater κ)를 낼 수 없다.
대신 **같은 사람이 같은 리뷰를 다시 라벨링했을 때 얼마나 일치하는가**를 낸다.

- 표본의 **10%** 를 무작위로 골라, 최초 라벨링 **3일 이상 뒤** 이전 라벨을 가린 채 재라벨링
- Cohen's κ 와 단순 일치율을 리포트에 싣는다
- κ 가 낮으면 그 자체가 결과다. **기준이 흔들렸다는 뜻이고, 분류기 점수의 상한이 된다.**
  이 경우 수치를 고치지 않고 "라벨 자체의 잡음이 X% 이므로 분류기 정확도의
  해석 가능한 상한은 Y% 이다"라고 적는다.

κ 해석 (Landis & Koch):

| κ | 해석 |
|---|---|
| < 0.40 | 낮음 — 이 라벨로 낸 수치는 신뢰하기 어렵다 |
| 0.40–0.60 | 보통 |
| 0.60–0.80 | 상당함 |
| > 0.80 | 높음 |

## 6. 개인정보

표본 파일에는 **실제 손님이 쓴 리뷰 원문**이 들어간다. 이 저장소는 공개다.

- `evaluation/sample_*.csv`, `evaluation/labels_*.csv` 는 `.gitignore` 에 있다
- 리포트에는 **집계 수치와 익명화·축약된 예시**만 싣는다
- 오분류 사례를 문서에 인용할 때는 매장·개인 식별 정보를 지우고, 원문 그대로가 아니라
  문제 유형이 드러나는 최소 길이로 줄여 쓴다
